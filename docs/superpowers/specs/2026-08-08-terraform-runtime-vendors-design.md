# Managing remote runtime vendors from Terraform

Since [#293](https://github.com/blossomstack/horsie/pull/293) the server builds cloud runtime
vendors itself: a Fly or velos vendor is a stored configuration rather than a process someone
runs, and `PUT /api/runtime-vendors/{name}` is the whole of how one comes into existence. That
makes it configuration in the same sense as a model provider or an MCP server, and configuration
horsie can create is configuration `terraform-provider-horsie` should be able to declare.

Today it cannot. The provider manages nine resources and none of them is a runtime vendor, so a
deployment can have its models, presets and environments under Terraform while the substrate all
of them run on is clicked into a settings page by hand.

This spec covers two changes in two repositories: a rename and a validation change in horsie, then
a new resource, a singleton resource and the provider's first data source in
`blossomstack/terraform-provider-horsie`.

## What horsie changes, and why it has to change first

The provider vendors Go types generated by `fluorite go` from `crates/models/fluorite`. It cannot
be written against a schema that does not exist yet, so horsie moves first and the provider
regenerates against it.

### The default-vendor API is renamed

`/api/config/default-vendor` becomes `/api/config/default-runtime-vendor`, `DefaultVendorInput`
becomes `DefaultRuntimeVendorInput`, and `SettingsView.default_vendor` becomes
`default_runtime_vendor`. "Vendor" alone is ambiguous the moment a provider resource has to be
called `horsie_model_provider` to avoid colliding with it; naming the concept once, in full,
everywhere it appears is cheaper than explaining the collision in each place.

The rename reaches every generated type tree — `clients/ts` **and** `clients/web/src/generated`,
of which CI guards only the first — the `ConfigStore` trait, the WebUI's settings and session-draft
code, the e2e setup, and the docs guide.

The `settings` table stores the value under the row key `'default_vendor'`. That key stays as it
is. It is storage rather than API, no client can observe it, and renaming it buys nothing but a
data migration whose failure mode is silently resetting every deployment's default vendor.

### `callback_url` is validated instead of rewritten

`normalise_callback` currently completes a bare origin: give it `wss://horsie.example.com` and the
row stores `wss://horsie.example.com/api/runtime/connect`. Terraform requires a Required attribute
to read back exactly what the configuration said, so that apply dies with `Provider produced
inconsistent result after apply`, and declaring the attribute Optional+Computed instead only turns
the error into a diff that never converges.

The completion is a typing affordance, not an API rule, so it moves to the WebUI form. The server
keeps every check it has — scheme, host present, loopback refused — and adds one more: a callback
URL with no path is refused, naming the path it wants.

```
the callback url must include the connect path, e.g. wss://horsie.example.com/api/runtime/connect
```

`normalise_callback` still trims surrounding whitespace, which is the same class of silent rewrite
and is left alone. Nobody writes a leading space into an HCL string, and a rule about it would cost
more to read than it could ever save.

## The provider

### Wire types

`make generate HORSIE_FLUORITE=<horsie>/crates/models/fluorite`, against a checkout carrying the
changes above. The Makefile runs `fluorite clean` first because generation overwrites but never
deletes. Expect churn beyond the vendor types wherever horsie has drifted since the last regenerate;
a compile error there is the outcome to want, since the alternative is a silent wire mismatch.

### `horsie_runtime_vendor`

The settings union maps to one nested block per kind. The block that is present *is* the kind, so
there is no discriminator to keep in sync with it, Terraform validates each kind's fields natively,
and a third substrate is a third block on the same resource rather than a new resource type.

```hcl
resource "horsie_runtime_vendor" "prod" {
  name       = "fly-prod"
  credential = var.fly_api_token

  fly {
    app            = "horsie-runtimes"
    image          = "ghcr.io/blossomstack/horsie-runtime:v1"
    region         = "iad"
    workspace_root = "/workspaces"
    callback_url   = "wss://horsie.example.com/api/runtime/connect"
    volumes        = true
    cpu_kind       = "shared"
    cpus           = 1
    memory_mb      = 1024
    volume_size_gb = 10
  }
}
```

Every field inside a block is Required. Horsie's wire types carry no optionals here and the server
applies no defaults on write — the `Default` impl in `runtime_vendor/config.rs` and the copy in
`CloudVendors.tsx` are both form prefill — so any default the provider offered would be a third
hardcoded copy of the same constants, and one that keeps writing stale values if horsie's ever
change. Sizing that provisions real machines is worth stating outright. The cost is that
`volume_size_gb` must be given even when `volumes = false`, where the server ignores it.

`name` is Required and replaces the resource when it changes: horsie refuses a body whose name
disagrees with the path rather than renaming a row, so there is no rename to perform.

`credential` is Optional and Sensitive. Null means "not managed here", which is exactly horsie's
"omitted keeps the stored token" — the same contract `horsie_model_provider.api_key` already has.
Create checks the attribute is set and fails with its own message rather than letting the server's
`a new runtime vendor needs a credential` surface as a 422 partway through an apply. It checks for
*set*, not for non-empty: velos deliberately supports a deployment with no auth, so `credential =
""` is a valid velos configuration even though the field cannot be omitted entirely.

`has_credential` is Computed. The token itself never comes back from the server, by design.

Exactly one block must be present, enforced by `ValidateConfig`. With none, the generated union
marshaller fails with `fluorite: RuntimeVendorSettings has no variant set` in the middle of an
apply; with both, the configuration is simply lying about what it wants. Both blocks are
config-only rather than Computed, so plain Go struct pointers are safe — the `types.List`
requirement applies to Computed nested attributes, which these are not.

`created_at` and `updated_at` are in the view and are left out of the schema. Neither is something
a configuration can act on, and `updated_at` would show fresh churn on every apply.

Import is by name. `credential` is null afterwards, which is the correct reading of an import: the
stored token is not managed here until something says otherwise.

Read filters `GET /api/runtime-vendors`, since horsie offers no per-name read — the same approach
`GetModelProvider` already takes for the same reason. A 404 drops the resource from state.

### `horsie_default_runtime_vendor`

```hcl
resource "horsie_default_runtime_vendor" "this" {
  vendor = horsie_runtime_vendor.prod.name
}
```

A singleton with one Required `vendor`, updated in place through the renamed `PUT` and deleted
through its `DELETE`, which reverts the server to `local`. Read comes from `GET /api/config`.

Two limits, both documented rather than defended against. Nothing stops two of these being declared
against one server, where they will fight on every apply. And because the server reports `local`
both when no default is set and when `local` is set deliberately, those two states are
indistinguishable on read.

### `data.horsie_runtime_vendors`

The provider's first data source, so `docs/data-sources/` is new.

It exposes the live roster from `GET /api/config` rather than the configured rows: `local`,
dialled-in `horsie connect` agents and configured vendors all appear, each with `name`,
`is_default` and `supports_provisioning`. That is the list that answers "what can an environment
target", and it is the only way to reference a vendor Terraform did not create. The configured rows
are already available as resource attributes and are not worth a second data source.

The vendors list is a `types.List` in the model. Every attribute of a data source is Computed, and
a Go slice cannot hold the unknown one carries before refresh.

## Verifying it

Unit tests in this provider run against an `httptest` fake built from the same vendored types, so
they agree with every mistake those types contain. They are worth having for verbs, URLs and
not-found handling, and they say nothing about whether the provider works. The ones that earn their
place:

- A model-to-union round trip per kind, built from a struct with no zero-valued fields, so a field
  added by a future `fluorite go` fails the test instead of being silently dropped on the wire.
- The `ValidateConfig` guard, for zero blocks and for both.
- The data source's hand-written `types.ObjectType` compared against `NestedObject.Type()` from the
  schema. The two drift silently otherwise.

The verification that finds bugs is an apply against a real server. Run a throwaway horsie with an
isolated state directory — `horsie-server` ignores `HORSIE_STATE_DIR` and will otherwise write to
the developer's real state:

```json
{ "storage": { "state_dir": "/tmp/tfvendor/state", "data_dir": "/tmp/tfvendor/data" } }
```

```
horsie-server --config /tmp/tfvendor/config.json --addr 127.0.0.1:3899
```

Log in with the password printed at first boot (also written to
`<state_dir>/server/initial-admin-password`), mint a device token with `POST /api/device/tokens`,
and drive `tofu` with a `dev_overrides` block pointing at a locally built binary. Apply a
configuration covering a Fly vendor, a velos vendor, the default-vendor resource and the data
source; then **assert an empty second plan**, which is the assertion that matters. An apply that
passes only demonstrates that the writes went through. Finish with an import round trip and a
destroy.

No Fly account is needed. Saving a vendor validates its settings and constructs an API client but
makes no call; machines are created when a session starts, which is outside this work.

## Delivery

Two pull requests, in order, each in its own worktree.

1. **horsie** — the rename and the `callback_url` change, including both generated type trees, the
   WebUI, the docs guide and the e2e setup. Verified across the whole workspace rather than
   `-p horsie-server`: the integration tests and the web e2e suite call these routes too.
2. **terraform-provider-horsie** — regenerate against merged horsie, then the client methods, the
   two resources, the data source, `examples/`, and `make docs`. `docs-check` fails CI on a stale
   tree.
