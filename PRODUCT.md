# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Developers and technical operators who self-host their own agent infrastructure. They run `horsie-server` on a machine they control — a homelab box, a workstation, a small VPS — bring their own model API keys, and point the agent at their own working directories or GitHub repos. They are comfortable with Docker, a terminal, and reading a tool call's raw JSON; they are not comfortable handing their source tree to a hosted product.

The job: **supervise long-running agent work on my own code, on my own machine, from a browser.** They start a session, hand it a task, and then watch, steer, interrupt, and audit it — often across tab closes, reconnects, and server restarts. A session is not a chat they read once; it is a run they come back to.

## Product Purpose

Run LLM agents as durable, event-sourced **sessions** in the browser, with tools executing in a **runtime** the user chose and controls. Every message, tool call, tool result, and status change is journaled server-side and replayed on reconnect, so closing the tab never loses a run that is still in flight.

Success is that a user trusts a long session enough to walk away from it: they can leave, come back, read exactly what the agent did and why, and take over at any point.

## Positioning

Self-hosted by construction, not as a deployment option. Two facts a hosted competitor cannot truthfully copy:

- **The runtime is the user's.** `horsie connect` runs on the user's own machine and dials *out* to the server, so the agent's tools execute against real local directories with no inbound networking, no upload, and no vendor in the path. The alternative, `velos`, provisions a throwaway container per session — but that is a choice the user makes per session, not a platform default.
- **The session is durable and inspectable, not ephemeral.** Sessions are event-sourced actors with a replayable journal, so "reconnect" is a first-class state rather than a reload. The transcript is the audit log.

## Operating Context

- Long-lived browser tab, usually docked beside an editor and a terminal on a desktop display. Sessions run for minutes to hours; users tab away and come back.
- The user has **two other windows for the same work**: their editor and their shell. The UI must not pretend to be an IDE — there is deliberately no file browser and no diff view.
- Two setup surfaces the user visits rarely but must not fear: **Settings** (providers, models, runtime vendors, GitHub, MCP, skill bundles, account) and **Admin** (model card catalog).
- Two configuration halves that never overlap: `config.json` (deployment/bootstrap, hand-edited) and the settings database (everything tuned day to day, edited in the UI).
- Auth is **on by default**; first boot generates an `admin` password written to `initial-admin-password` in the state directory. A device-approval flow exists for CLI login.

## Capabilities and Constraints

Confirmed functionality the redesign must preserve:

- **Sessions** — list with live status (idle / updating / error), search, create, open, stop mid-turn, delete. Titles auto-generate. History paginates: recent messages load instantly, older ones load on scroll-up.
- **Transcript** — grouped assistant turns; streaming reply text; collapsible tool-call rows exposing raw input and output; thinking blocks shown after a turn completes (hidden by default, toggleable); a work-group row condensing multi-step activity; interactive `ask_user` cards (clickable / multi-select) answered inline.
- **Session config** — an inline toolbar (not a modal) for model, runtime vendor, repos + refs, plugins/skills, MCP servers. A new session is a client-side draft until the first message is sent.
- **Side panels** — cumulative token usage (a running total, explicitly *not* a context-fullness meter) and a live agent task list that appears only once the agent uses the tool and collapses to a completed/total badge.
- **Settings** — 6 pages (models, runtimes, skills, memory, integrations, account) split by save boundary, because `SettingsUpdate` fields replace per-collection. Plus admin model cards and agent presets.
- **Auth** — login, device approval, password change.

Technical constraints:

- React 19 + Vite + Tailwind v4 + TypeScript, React Router (BrowserRouter), TanStack Query, Radix Dialog, lucide-react icons, react-markdown + highlight.js. Vitest unit tests and a Playwright e2e suite drive real DOM; both must stay green.
- All wire types are generated by fluorite from `models/fluorite/*.fl` into `src/generated` — never hand-edit, never restructure.
- Transport is HTTP + a single SSE `/events` stream with journal-seq cursors. The UI has no other data source.
- Light and dark themes are both first-class and runtime-swappable via `data-theme` on `<html>`.
- Ships as static assets served by the Rust binary at `clients/web/dist`; no SSR, no server-rendered HTML, no external font CDN assumed at runtime.
- Old routes (`/skills`, `/memory`) redirect to their settings homes; bookmarks must keep working.

## Product Principles

1. **The transcript is the product.** Everything else is chrome around a run the user must be able to read, audit, and trust.
2. **Show the machinery, don't hide it.** These users want to see the tool call, the raw output, the token cost, the runtime it ran on. Progressive disclosure, never concealment.
3. **Reconnect is a normal state, not an error.** Durability is the differentiator; the UI should make "this survived" visible rather than incidental.
4. **Never pretend to own the user's machine.** No file browser, no diff view, no IDE cosplay. The UI's job ends where the editor's begins.
5. **Setup is rare and high-stakes.** Settings must be safe, reversible, and explicit about what half of the config it owns.

## Accessibility & Inclusion

No user-specific requirement has been established. Baseline obligations apply: full keyboard operation of the primary loop (compose, send, stop, navigate sessions), visible focus, WCAG AA contrast in both themes, and status never conveyed by color alone — the last matters because session state (idle / updating / error) is currently a colored dot.
